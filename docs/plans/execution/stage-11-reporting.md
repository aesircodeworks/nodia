## T9: reporting:rebuild command with --tenant, --verify, and the projector advisory lock

2026-07-13 04:26 -03

Landed stage-11 plan task breakdown item 13, TDD sequencing Slice 7 in full, and exit criteria 3 and 4. Not an endpoint (the task's own instruction and the plan's Method section both say so): no laravel-data class, no OpenAPI path, no `composer types:generate` step, mirroring T1's own "no wire boundary, contract step doesn't apply" posture.

What landed:

- `App\Support\Outbox\ProjectionLock`: the per-projection PostgreSQL advisory lock, in `App\Support\Outbox` rather than `App\Reporting` because `App\Support\Outbox\Jobs\ProcessOutboxDelivery` needs to call it and Support cannot import a bounded context (architecture rule). Session-scoped (`pg_advisory_lock`/`pg_advisory_unlock`), not transaction-scoped: the command's exclusive hold spans several tenant-scoped transactions in one run (one `asTenant()` per tenant), which `pg_advisory_xact_lock` cannot hold across since it releases at each transaction's own commit. The shared side (`pg_try_advisory_lock_shared`/`pg_advisory_unlock_shared`) is acquired and released tightly around one projector effect inside its own single tenant transaction. Keyed by `hashtext()` of a fixed namespace string plus the projection name, using Postgres's two-int4-argument advisory lock functions.
- `App\Support\Outbox\ProjectionLockedSubscriber`: a marker interface (`projectionLockKey(): string`), mirroring `OrderedOutboxSubscriber`'s own precedent for a subscriber-declared behavior `ProcessOutboxDelivery` checks for.
- `App\Support\Outbox\Jobs\ProcessOutboxDelivery`: now also takes `ProjectionLock` in `handle()`'s signature. When the resolved handler implements `ProjectionLockedSubscriber`, it attempts the shared lock immediately before the conditional `markProcessed()` (so a failed attempt leaves the delivery untouched, not marked and not applied) and releases it in a `finally` immediately after the effect runs. A failed attempt defers with the same `outbox.ordered_defer_seconds` backoff `OrderedOutboxSubscriber` deferrals already use, and, on the final attempt, returns cleanly instead of failing so the delivery remains pending for the reconciliation sweeper (task's own instruction: "reuse whatever Stage 4 landed for job-release plus the sweeper backstop"). The private method that does this was renamed from `deferOrdered()` to `defer()` since it now serves two distinct deferral reasons with identical backoff semantics; its docblock says so.
- `App\Reporting\Support\Rebuild\RebuildableProjection`: a new interface (`name()`, `modelClass()`, `keyColumns()`, `computeIncrement()`, `keyFor()`, `fold()`, `rowFromModel()`) that `ProjectDailySales`, `ProjectEventFinance`, and `ProjectEventAttendance` now implement alongside `OutboxSubscriber` and `ProjectionLockedSubscriber`. Each job's `handle()` was refactored into a `computeIncrement()` step (pure resolution, no write) and an apply step (`ApplyXIncrement`, unchanged); `handle()` now just calls both. This means the exact same payload-resolution logic (the Orders and Payments bulk-lookup Actions) backs both the live delivery path and the rebuild path, so there is exactly one place that decides what an event means to a projection, never two divergent implementations.
- `App\Reporting\Support\Rebuild\InMemoryProjectionAggregate`: folds a sequence-ordered event stream into the same commutative row state the live SQL upsert produces, entirely in PHP memory, by calling `computeIncrement()`/`keyFor()`/`fold()` on the resolved `RebuildableProjection`. `ProjectEventAttendance::fold()`/`rowFromModel()` format the two scan-timestamp bounds as fixed-width UTC ISO 8601 strings (`Y-m-d\TH:i:s.u\Z`) and fold them with plain PHP `min()`/`max()` that reproduce Postgres's `LEAST`/`GREATEST` null-ignoring semantics exactly, so the in-memory path needs no database to compute the same bounds the live upsert would.
- `App\Reporting\Support\Rebuild\ProjectionDrift`: a plain value object (`missingCount`, `extraCount`, `mismatchedCount`, `total()`, `isClean()`).
- `App\Reporting\Support\Rebuild\ReportingProjectionRebuilder`: the service wrapping the Stage 4 primitive. `eventsFor(string $projectionName)` resolves the registered subscriber (throws `LogicException` if it is not a `RebuildableProjection`) and returns `OutboxReplay::eventsFor($types)` verbatim, no re-sorting or re-filtering. `rebuild(string $projectionName, ?string $tenantId)` deletes the projection's rows and replays them through the handler's own `handle()`, one tenant at a time inside that tenant's own `asTenant()` transaction (delete and replay commit together per tenant; RLS's write-under-app-role requirement makes a tenant-scoped transaction the natural atomic unit here, not one transaction spanning every tenant, since `asTenant()` itself always opens its own transaction). When no `--tenant` is given, the target tenant set is the distinct `tenant_id`s present in the eligible event stream itself, not a fresh read of the `tenants` table: a projection row can only ever exist because some subscribed event created it, and `outbox_events` rows are never deleted, so this is a safe, complete universe without Reporting ever touching Tenancy's own table. `verify(string $projectionName, ?string $tenantId)` builds an `InMemoryProjectionAggregate` per tenant and diffs it against a live `SELECT` of that tenant's rows (read-only; never applies an increment through `ApplyXIncrement`).
- `App\Console\Commands\ReportingRebuildCommand`: `reporting:rebuild {projection} {--tenant=} {--verify}`. `{projection}` is the projection's registered `SubscriberRegistry` name (`project_daily_sales`, `project_event_finance`, `project_event_attendance`), the same identifier `outbox:replay {subscriber}` already uses for the analogous concept, rather than inventing a second naming scheme. Takes `ProjectionLock::acquireExclusive($projection)` before any work and releases it in a `finally` after, wrapping both the rebuild and the verify path. `--verify` prints the drift counts and returns `FAILURE` (a nonzero exit code) when drift is nonzero, so the command is script-friendly; a `LogicException` from an unknown or non-rebuildable projection name is caught and reported as a command error rather than an uncaught stack trace.

Deviations from the plan, disclosed:

1. The plan's own prose (Endpoints table row, Risks section) does not name the exact shape of "in-memory aggregates" for `--verify`; I built a genuine per-projection in-memory fold (`InMemoryProjectionAggregate` plus each job's own `fold()`/`rowFromModel()`), not a database-transaction-with-rollback shortcut. I considered the rollback shortcut (open a transaction, replay for real, diff, roll back) since it would reuse the exact same code path as `rebuild()` with less new code, but the task's own wording is explicit that `--verify` "replays into in-memory aggregates ... without writing" as the mechanism, not merely as an observed property, and a real in-memory fold also means `--verify` takes no row locks and issues no writes at the SQL level at all, which is the safer posture for a mode whose whole purpose is to run against a live, possibly-contended table.
