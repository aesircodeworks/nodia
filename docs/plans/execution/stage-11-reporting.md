Decisions and deviations, disclosed in full:

1. `ExportNotFoundException` deliberately maps to the generic `ErrorCode::RequestNotFound` rather than a new `export_not_found` code, a real departure from this codebase's otherwise near-universal per-resource-not-found-code convention (`RefundNotFound`, `OrderNotFound`, `HoldNotFound`, `AssignmentNotFound`, and every other `find() ?? throw XNotFoundException` site in every controller in this codebase name their own code). Two independent signals point the same direction: the stage-11 plan's own Endpoints table row writes "404 (standard) when unknown or cross-tenant" for this one endpoint, the only row in the entire plan phrased that way instead of naming a code (contrast stage-8b's "404 `refund_not_found`" for the analogous `GET /v1/refunds/{refund}`); and this task's own instructions enumerate exactly two new codes to register in the Stage 1 registry (`export_not_ready`, `export_failed`), naming no third one for not-found. Verified this reading has a real, load-bearing precedent already in the codebase, not just a plausible guess: `App\Payments\Exceptions\PayoutNotFoundException` and `SubmerchantAccountNotFoundException` (stage-8c) both already map to `ErrorCode::RequestNotFound` by explicit design, each with a docblock stating exactly this "deliberately maps to the generic code" reasoning, so this is a following an established, if less common, pattern rather than inventing one.
2. `DB::afterCommit()` around dispatching `BuildExportJob` (detailed in "What landed" above) is not a style preference; without it, `TenantTransaction::run()`'s own nested-transaction guard would throw a `LogicException` the moment the sync queue (every test and dev environment) tried to execute the job inline, mid-request, still inside `ResolveTenantFromHeader`'s own open transaction. Verified by first writing `CreateExport` without the deferral and watching the exact `LogicException` fire on the very first POST test; fixed by mirroring `OutboxDispatcher`'s and `InviteUser`'s existing `DB::afterCommit()` precedent, not a new pattern invented for this task.
3. A real, disclosed bug caught while writing `ExportLifecycleTest.php`'s and the contract exercisers' completed-download fixtures: attaching a header-only CSV (`"id\n"` or similar) to the `export_file` medialibrary collection is rejected by `FileUnacceptableForCollection`, because PHP's fileinfo mime-sniffing detects a single comma-light line as `text/plain`, not `text/csv` (confirmed empirically with a throwaway `finfo_file()` probe before fixing, the same discipline T11's own journal used to verify the opposite case). This is not a bug in `App\Reporting\Actions\BuildExport` or `CsvExportWriter` themselves (a real multi-row export, which is what every actual source produces, sniffs correctly, as T11 already verified), only a hazard for a test fixture that fabricates a too-minimal file directly rather than running a real source; fixed by attaching a genuine two-line CSV (header plus one data row) in both `ExportLifecycleTest.php`'s `completeExport()` and the contract suite's `contractCompleteExport()`. Recorded here because it is a real defect this task's own test-writing surfaced, not a design decision.
4. `completeExport()`/`failExport()` (Feature test) and `contractCompleteExport()` (Contract test) drive `App\Reporting\Models\Export`'s own `claim()`/`complete()`/`fail()` transitions directly rather than a real registered `ExportSource`, a deliberate scope choice disclosed rather than silently taken: the real end-to-end build pipeline (a registered source's `pages()` actually iterating, `BuildExport` actually attaching the file) is already exhaustively covered by T11's `OrdersExportTest` and T12's three sibling tests, so re-driving it here would duplicate coverage without adding any assurance about the endpoint surface this task actually owns. An earlier draft of `failExport()` did register a fake, always-throwing `ExportSource` over the real `orders` entry (T11's own `OrdersExportTest` precedent) and drove `BuildExport` for real; this caused one genuine test-ordering failure (a later "completed" test unexpectedly found the export already `failed`), traced to the registration mutating the container-bound `ExportSourceRegistry` singleton in a way that leaked across tests in the same file. Rather than chase down the exact mechanism (Pest's default test order within a `describe` block is not strictly top-to-bottom declaration order in this suite, confirmed by observing the failing test ran after the poisoning one despite being declared first), the simpler and strictly more isolated fix was to stop touching the shared registry at all for this file's own fixtures, which is what the "What landed"/Decision 3 approach does.
5. No other deviation from the plan's task-16 description or this task's own instructions.
