### T5: Purchase-limit enforcement in the hold lifecycle (2026-07-12)

Landed the feature and concurrency halves of TDD Slice 3 (stage-10 plan, task breakdown item 6; depends on T5's own listed dependency, T4, already landed):

- Additive migration `2026_07_12_000055_add_counted_quantity_to_hold_items_table.php` adds `hold_items.counted_quantity` integer, non-null, `DEFAULT 0` (every pre-existing row and every unlimited item reads back "never counted" with no backfill Action), plus a `hold_items_counted_quantity_non_negative` CHECK as defense in depth (no CHECK ties it to `quantity`: that relationship can only be proven false by `CreateHold`'s own construction, not exempted like a nullable column). `App\Inventory\Models\HoldItem` gained the property and its `Fillable` entry.
- `App\Inventory\Actions\CreateHold` wiring: `assertHoldable` (already looping every item before any mutation) gained a `?string $customerId` parameter and now throws the new `CustomerRequiredException` (422 `customer_required`) when an item's `HoldableTicketTypeData::maxPerCustomer` is set and no customer is authenticated, before any inventory statement runs. A new private `claimPurchaseLimit` runs immediately after each item's existing held-increment guard (`claim()`), inside the same transaction: a no-op returning 0 for an unlimited ticket type; otherwise it calls `App\Inventory\Support\PurchaseCounters::increment` with the ticket type's `maxPerCustomer` as the limit and returns the item's own quantity as `counted_quantity`, which `HoldItem::create` now persists. Zero affected rows from the guard throws the new `PurchaseLimitExceededException` (409 `purchase_limit_exceeded`, extension members `ticket_type_id` and `limit` via `HasProblemExtensions`, the same pattern `SubmerchantAlreadyOnboardedException` already established, not `HasValidationErrors`'s `errors` map shape, since the plan calls these two scalar top-level members rather than a map).
- A real bug caught by the concurrency test before it was written: `App\Inventory\Support\PurchaseCounters::increment`'s `INSERT ... ON CONFLICT DO UPDATE ... WHERE` guard (T4) only ever applies its `WHERE` clause to the `UPDATE` branch; Postgres inserts the conflict-free first row unconditionally. A customer's very first hold against a limited ticket type could therefore request an unbounded quantity and have it counted with no guard at all. This is exactly what the stage-10 plan's own Data model section already flags: "The insert path is guarded by request validation (`:n <= :limit`, deterministic, no race)." `claimPurchaseLimit` now checks `$item->quantity > $ticketType->maxPerCustomer` and throws `purchase_limit_exceeded` before calling `increment` at all, which is exactly the `n <= limit` case for a counter starting at zero; combined with the upsert's own `WHERE` on every later conflict, both insert and update branches enforce the same invariant. Caught by the very first run of the mandated concurrency test (a single request for 3 units against a limit of 2 wrongly returned 201), not discovered later, matching the master plan's "tests first" discipline.
