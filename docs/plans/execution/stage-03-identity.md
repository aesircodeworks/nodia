#### task-01: Passport install and configuration (2026-07-09)

Verified current Passport documentation (context7 `/laravel/passport`, pinned `13.x` docs, cross-checked against the installed `v13.7.5` source under `vendor/laravel/passport`) before writing any code, per the plan's Risks item:

- Password grant: available but disabled by default since Passport 12.0; requires an explicit `Passport::enablePasswordGrant()` call. Confirmed fit for the stage's design; the fallback (first-party token controller not using the password grant type) is not needed. A first-party `/v1/auth/*` controller is still built in task-02, but it drives Passport's `AuthorizationServer` directly with `grant_type=password` rather than exposing Passport's own `/oauth/token` route, which is disabled via `Passport::ignoreRoutes()` so it cannot leak the OAuth-shaped contract Passport ships by default.
- Provider binding: `passport:client --provider=` and `ClientRepository::createPasswordGrantClient($name, $provider, $confidential)` bind a client to a named entry in `config('auth.providers')`; a client's `provider` column is read from `oauth_clients` and compared against the authenticating guard's provider name at token-issuance and resource-request time. Confirmed sufficient for the two-population design without any Passport source changes.
- JWT claim customization: Passport's `AccessTokenTrait::convertToJWT()` (`league/oauth2-server`) is a private trait method, not overridable by subclassing `Laravel\Passport\Bridge\AccessToken`. The supported extension point is `Passport::useAccessTokenEntity()` with a custom entity overriding the public `toString()` method, which task-02 will use to add `identity_type` and (for customers) `tenant_id` claims. Recorded now because it determines task-02's approach; no code needed yet since no endpoint ships this task.
- Refresh token internals: `oauth_refresh_tokens` has no reuse-detection concept built in beyond `revoked` and `Passport::$revokeRefreshTokenAfterUse`; the family-revocation semantics the stage plan wants (revoke every live token in the family on reuse) need custom code around `RefreshTokenRepository`, confirmed as task-03's job, not something Passport provides directly.

No fallback triggered: Passport's password grant is fit for purpose as designed in the stage plan.

- Passport's five published oauth migrations (`oauth_auth_codes`, `oauth_access_tokens`, `oauth_refresh_tokens`, `oauth_clients`, `oauth_device_codes`) are all kept for parity with Passport's own model expectations, even though the device grant is unused; `user_id` columns changed from `foreignId` (bigint) to `uuid` on the three tables that carry one, matching the uuid primary key shared by `users` and the future `customers` table. `oauth_clients.owner` morphs changed from the default bigint morphs to `nullableUuidMorphs` for the same reason. Two deviations from a literal reading of the plan, both investigated against vendor source before deciding, in the spirit of task 1's Passport verification:

1. **The `/v1/auth/staff/token` controller cannot expose Passport's OAuth-shaped request directly** (already established by task 1), so `App\Identity\Actions\IssueStaffToken` builds a synthetic `Illuminate\Http\Request` with `grant_type=password`, the seeded staff client's id, and the caller's email/password, converts it to a PSR-7 request via `Symfony\Bridge\PsrHttpMessage\Factory\PsrHttpFactory`, and calls `AuthorizationServer::respondToAccessTokenRequest()` directly. `Laravel\Passport\Client::password_client` turned out to be a virtual accessor derived from the `grant_types` column (Passport's current published migration has no such column; task 1's decision journal predates this discovery), not a queryable database column, so the client lookup is by `provider` alone (exactly one password-grant client is seeded per provider by task 1, so this is unambiguous) rather than `where('password_client', true)`, which raised `column "password_client" does not exist` against real Postgres. `League\OAuth2\Server\Exception\OAuthServerException::invalidCredentials()` (bad username or password, and Passport's `Bridge\UserRepository` never distinguishes an unknown email from a wrong password) carries the OAuth error type `invalid_grant`, not a type literally named `invalid_credentials`; the action maps only that error type to the stage's `invalid_credentials` code (401) and rethrows anything else, so a genuinely broken client or grant configuration surfaces as a 500 instead of masquerading as a login failure.

2. **JWT claim customization needed a structural fix beyond task 1's plan.** `Passport::useAccessTokenEntity()` is declared `class-string<Laravel\Passport\Bridge\AccessToken>`, so a class only implementing `AccessTokenEntityInterface` (composing the three league/oauth2-server traits directly, which was the first approach, chosen because `AccessTokenTrait::convertToJWT()` and the private `$privateKey`/`$jwtConfiguration` state it needs are private to whichever class composes the trait and therefore unreachable from a plain subclass of `Bridge\AccessToken`) fails Larastan with `argument.type` rather than being silently accepted; PHPStan's own instructions forbid suppressing this with a cast, an ignore comment, or a baseline entry. The fix that satisfies both constraints: `App\Identity\OAuth\IdentityAccessToken extends Laravel\Passport\Bridge\AccessToken` (satisfying the `class-string` bound structurally) and separately re-composes `League\OAuth2\Server\Entities\Traits\AccessTokenTrait` in the child (giving the child its own private `$privateKey`/`$jwtConfiguration`/`initJwtConfiguration()`/`convertToJWT()`-equivalent state, shadowing the parent's inaccessible copies, since PHP trait composition in a subclass takes precedence over inherited parent methods of the same name); the other trait members it needs (`getClient()`, `getIdentifier()`, ...) are `protected` in `TokenEntityTrait`/`EntityTrait` and stay inherited from `Bridge\AccessToken` without recomposition. `toString()` duplicates `AccessTokenTrait::convertToJWT()`'s claim set (`aud`, `jti`, `iat`, `nbf`, `exp`, `sub`, `scopes`) and adds whatever `App\Identity\OAuth\IdentityClaims::for($provider)` returns, keyed off the issuing client's `provider` (`Laravel\Passport\Bridge\Client::$provider`, a public property already carrying `'users'` or `'customers'`); `IdentityClaims` is a pure function so it is unit-tested directly without touching JWT signing or the database. Registered via `Passport::useAccessTokenEntity(IdentityAccessToken::class)` in `IdentityServiceProvider::boot()`.

**Genuine blocker resolved rather than deferred: RSA key provisioning, flagged but explicitly left open by task 1.** `league/oauth2-server`'s `AbstractGrant::issueAccessToken()` and `Lcobucci\JWT`'s `BearerTokenValidator` both require real key files (or configured key contents) the moment any token is issued or validated, and neither the app image, `make setup`, nor CI provisioned them; the first attempt to hit the new endpoint failed with "Private key is empty" equivalent errors. Fixed with a self-contained test harness fix mirroring the existing `Tests\Support\MigratedDatabase` pattern: `Tests\Support\OAuthKeys::ensure()` runs `passport:keys --force` once per test process if `storage/oauth-{public,private}.key` are missing, called from `Tests\TestCase::setUp()` (covering Feature, Unit, Contract, Isolation, and Concurrency, since all extend `TestCase`; Architecture does not need it and does not boot the framework). This means CI needed no changes: every job that runs Pest suites already boots through `TestCase`. Also added the same idempotent `passport:keys` step to `make setup` (guarded like the adjacent `key:generate` step) for host-based local dev; the live Docker Compose `api` service's own key provisioning is not addressed (no task in this stage's plan currently exercises `POST /v1/auth/staff/token` against the running container, and the CLAUDE.md-mandated verify command is only `/v1/health`), so this remains an open item if a later task needs the live stack to issue tokens.

**A second, adjacent blocker discovered and resolved while proving the "rejected 901 seconds later" requirement**: `league/oauth2-server`'s `AbstractGrant::issueAccessToken()` sets the `exp` claim from `(new DateTimeImmutable())->add($accessTokenTTL)` and `Lcobucci\JWT`'s `BearerTokenValidator` validates it against its own hardcoded `new DateTimeImmutable('now', ...)` clock (confirmed by reading both classes' source before writing any test code); neither goes through Carbon, so Laravel's `freezeTime()`/`travel()` test helpers, which only patch `Carbon::setTestNow()`, have no effect on a Passport-issued JWT's expiry in either direction. This is intrinsic to the two vendor libraries, not something reachable through `Passport::useAccessTokenEntity()`'s claim-set extension point without also overriding `setExpiryDateTime()`/replacing the validator's clock, which would diverge production behavior from what is tested. Deviation taken: the `expires_in: 900` value is asserted directly and tied to `config('identity.access_token_ttl_minutes')` (not restated as a literal magic number) in the feature test; the "rejected once past expiry" requirement is proven by decoding a genuinely issued access token, rebuilding a new JWT carrying the same `jti` (so it still resolves as a live, non-revoked row in `oauth_access_tokens`, the same check `BearerTokenValidator::isAccessTokenRevoked()` performs) and the same `sub`/`aud`/`scopes`/`identity_type` claims but with `iat`/`nbf`/`exp` moved into the past, signed with the app's real private key, and asserting `GET /v1/me` rejects it with `auth.unauthenticated`. This exercises exactly the `LooseValidAt` validation branch that will reject the real token 901 seconds after issuance, deterministically, without sleeping or attempting to fake wall-clock time inside a vendor library that does not support it.

`response()->json($data, ...)` is used explicitly for the token endpoint's controller rather than returning the `TokenPairData` object directly from the controller (the pattern used everywhere else, including `GET /v1/me`): `Spatie\LaravelData\Concerns\ResponsableData::calculateResponseStatus()` defaults a POST response to 201, which is correct for `POST /v1/tenants` (creates a resource) but wrong for a token exchange (issues a token, creates nothing addressable), caught by the feature test asserting `assertOk()` against an initial 201.

#### task-03: Slice 2, refresh rotation, reuse detection, logout (2026-07-09)

Built the feature tests first (`tests/Feature/Identity/StaffRefreshTest.php`, `tests/Feature/Identity/StaffLogoutTest.php`), then the contract (`RefreshTokenRequestData`, reusing `TokenPairData` from task-02, the two new OpenAPI paths, and a combined `RefreshTokenProblem` schema following the `TenantDomainConflictProblem` precedent from Stage 2 for a status that can carry either of two codes), then the concurrency test first for the rotation guard (`tests/Concurrency/StaffRefreshRotationContentionTest.php`), then the unit tests for the family-revocation logic (`tests/Unit/Identity/RefreshTokenFamilyRevocationTest.php`), then implemented to green, per the double loop.

Endpoints shipped: `POST /v1/auth/staff/refresh` (unauthenticated; `RefreshTokenRequestData` in, `TokenPairData` out, mirroring `IssueStaffToken`'s approach of driving `AuthorizationServer::respondToAccessTokenRequest()` directly with `grant_type=refresh_token`) and `POST /v1/auth/staff/logout` (staff bearer; 204).

Core design, investigated against `league/oauth2-server` and Passport source before writing any code, per the plan's Risks item "Reuse detection semantics":

- **Family tracking.** A new `family_id` column on `oauth_refresh_tokens` (migration `2026_07_09_000010`, a plain `ALTER TABLE` since the table already merged in task-01 and per CLAUDE.md merged migrations are never edited) threads every refresh token issued from one login through every rotation that follows it. `App\Identity\OAuth\IdentityRefreshTokenRepository extends Laravel\Passport\Bridge\RefreshTokenRepository`, bound in `IdentityServiceProvider::register()` against the concrete class name (not the interface): `PassportServiceProvider` resolves `Bridge\RefreshTokenRepository::class` via the container for both the password grant (login) and the refresh grant (rotation), so one binding reaches every code path that creates or rotates a refresh token. `family_id` is `uuid` and NOT NULL with no default: refresh token ids themselves are league's own 40-character hex strings, not valid uuids, so a brand-new login's token gets a fresh `Str::uuid()`, never its own identifier (a first attempt reusing the token's own id as its family id failed with a Postgres `invalid input syntax for type uuid` error against real Postgres, caught by the first test run). No backfill concern: this table carries no production traffic yet.
- **Rotation guard (Slice 2 Concurrency).** `revokeRefreshToken()` overrides Passport's unconditional `update(['revoked' => true])` with a conditional `UPDATE ... WHERE id = ? AND revoked = false`, checked by affected-row count, never read-then-write, mirroring the `RemoveDomain`/`TenantDomainContentionTest` pattern from Stage 2. The concurrency test (two parallel `/v1/auth/staff/refresh` calls presenting one refresh token, driven through the real HTTP kernel in forked workers per `ParallelRunner`) proves exactly one 200 and one 401. The loser's specific error code is not pinned to a single value: `league/oauth2-server`'s `RefreshTokenGrant::validateOldRefreshToken()` calls `isRefreshTokenRevoked()` (a plain read) *before* the grant ever reaches the conditional-UPDATE guard, so depending on exactly how the two requests interleave, the loser is rejected either at the guard itself (`invalid_refresh_token`, this class's own `RaceLostHint`) or earlier, because the winner's commit already landed by the time the loser's own revoked-check runs (`refresh_token_reused`, `VendorRevokedHint`). Both are asserted as acceptable in the concurrency test with a comment explaining why; the invariant that is unconditionally guaranteed regardless of interleaving, and the one actually asserted strictly, is that exactly one requester's conditional UPDATE can ever flip `revoked` false to true for one row.
- **Reuse detection and family revocation.** `isRefreshTokenRevoked()` treats any presentation of an already-revoked token as reuse (the revoked flag alone cannot distinguish a legitimate past rotation from a captured, replayed token) and calls `App\Identity\Actions\RevokeRefreshTokenFamily`, which revokes every currently-live refresh token in the family and the access token issued alongside each one, via two UPDATEs both conditioned on `revoked = false` (naturally idempotent under replay or concurrent replay of the same stale token). The rotation guard's race-loser is deliberately *not* routed through this path: `RotateStaffToken` distinguishes the two failure hints and only maps `VendorRevokedHint` to `refresh_token_reused` per the design point above, so a benign concurrent double-call never revokes the winner's brand-new pair. This is stricter than Passport's default single-token revocation, exactly as the plan's Risks item anticipates.
- **Logout** (`App\Identity\Actions\RevokeStaffSession`) revokes only the presented session's access token (via Passport's own `AccessToken::revoke()`) and its one live refresh token (`WHERE access_token_id = ? AND revoked = false`), deliberately not the whole family: a legitimate logout must not cascade into revoking other sessions for the same user, proven by a dedicated feature test logging in twice and confirming the second session survives the first session's logout.

**Blocker investigated and resolved within this task, not deferred: a Laravel testing artifact, not a production bug.** The first run of both `StaffLogoutTest` and `StaffRefreshTest`'s multi-request scenarios failed with a revoked bearer token still authenticating successfully on a second `GET /v1/me` call within the same test method. Root-caused (not guessed) by a reproduction script confirming the DB row was genuinely `revoked = true` while the HTTP response was still 200: `Illuminate\Auth\AuthManager::guard()` caches a resolved guard instance (`$this->guards[$name] ??= ...`) for the life of the container, and `Illuminate\Auth\GuardHelpers` caches the resolved `$user` on first success; Laravel's HTTP testing helpers do not rebuild the application between `$this->postJson()`/`$this->getJson()` calls within one test method (only between test methods), so a guard resolved during an earlier call in the same test keeps returning its cached user on a later call regardless of what bearer token that later request actually presents. Confirmed as test-only by reproducing the fix with `Illuminate\Support\Facades\Auth::forgetGuards()` inserted between the state-changing call and the next authenticated assertion, which is now called at each such point in both files with a comment explaining why; a real deployment boots a fresh application per request and has no equivalent problem. Flagged here in case it recurs in later Stage 3 slices that also chain multiple authenticated calls in one test (MFA, membership endpoints).

No isolation coverage this task: no new tenant-scoped table (the `family_id` addition lands on the existing unscoped `oauth_refresh_tokens` table, matching the Stage 3 plan's sanctioned Passport-infrastructure exception already covered by `tests/Unit/Identity/PassportMigrationsTest.php`).

#### task-04: memberships and roles schema, Capability enum, template seeder (2026-07-09)

Pure migration task per the plan (task breakdown item 4): no endpoint routes to `memberships` or `roles` yet, so this task's TDD loop is isolation tests first, then migrations and models, then unit tests for the two named invariants, with no feature/contract loop (no wire endpoint exists this task).

Migrations, in dependency order: `2026_07_09_000011_grant_users_table_to_rls_roles.php`, `2026_07_09_000012_create_roles_table.php`, `2026_07_09_000013_create_memberships_table.php`, `2026_07_09_000014_seed_template_roles.php`.

- **`roles`**: nullable `tenant_id` (the sanctioned exception), `capabilities` jsonb, `unique(tenant_id, name)` plus the partial `roles_template_name_idx` on `name` where `tenant_id is null` (Postgres treats NULLs as distinct under a normal unique index, so the plain unique constraint alone never catches two templates sharing a name). RLS is hand-written rather than through `Rls::applyTenantPolicies`: a `roles_template_or_tenant_read` SELECT policy admitting `tenant_id is null or tenant_id = app.tenant_id`, three separate `roles_tenant_insert`/`_update`/`_delete` policies (each requiring `tenant_id = app.tenant_id`, which a NULL `tenant_id` row can never satisfy, so nodia_app can never mutate a template at the database level), and `roles_platform_write for all to nodia_platform using (true) with check (true)`, the one write path a template row can ever satisfy.
- **`memberships`**: `unique(user_id, tenant_id)`, `scope` a plain string column backed by the new `App\Identity\Enums\MembershipScope` enum (`tenant`, `platform`) via an Eloquent cast. RLS is the plain `Rls::applyTenantPolicies('memberships')` (no `platformWrite`: the plan calls this "standard single-table policy," and membership mutation is tenant admin surface for a future `InviteUser`/`AssignRole` Action running under `nodia_app`, not platform-admin surface the way `tenant_domains` is) plus one extra hand-written permissive SELECT policy, `memberships_self_read`, matching `user_id = current_setting('app.user_id', true)::uuid`. Postgres ORs multiple permissive policies together for the same command, so this only ever widens SELECT visibility past the tenant policy, never past it for INSERT/UPDATE/DELETE, proven by a dedicated isolation test asserting a `nodia_platform` write outside any asserted tenant context still affects zero rows.
- **`Identity/Capability.php`**: the ten-entry initial registry the plan names, plus `isFinanciallyPrivileged(): bool` marking `OrdersRefund` and `PayoutsView` (system-design 5.1/5.4: "MFA is mandatory for platform-scope staff and for tenant roles that include payout or refund permissions"; MFA's own enforcement mechanism is a later Stage 3 task, this only seeds the flag on the registry now so the two never drift apart). Locked down by a Unit test asserting the exact registry list and the exact financially-privileged subset, so a later stage extending the enum gets a loud diff instead of a silent rename.
- **Template seeder**: `App\Identity\Actions\SeedTemplateRoles`, keyed on `(tenant_id: null, name)` via `updateOrCreate`, so repeated invocation is idempotent by construction. `2026_07_09_000014_seed_template_roles.php` runs it once under `nodia_platform` inside the migration (same data-migration pattern as the tenants sentinel row and the task-01 Passport clients: tracked like every other schema change, not a re-runnable `Database\Seeders` class), and `tests/Unit/Identity/SeedTemplateRolesTest.php` calls it a second time after `MigratedDatabase`'s `migrate:fresh` already ran it once, asserting the row count and every capability set are unchanged. Designed the five templates' capability sets myself, since the plan names only the five role titles: Owner gets every capability except `tenants.manage` (platform-only concern); Event Manager gets the event and order-view/check-in surface without financial or membership capabilities; Box Office gets order view, event view, and check-in; Finance gets the two financially privileged capabilities plus order/event view; Check-in Agent gets only `checkin.scan` and `events.view`. Recorded here as a design decision open to revisit once task-08/09 build the role endpoints that make these sets user-visible.
- **`scope = platform` implies sentinel tenant invariant**: the plan says this is "enforced in the Action," but no Action creates real `Membership` rows until task-09 (`InviteUser`/`AssignRole`). Enforced now at the model layer instead: `Membership::assertScopeInvariant(MembershipScope $scope, string $tenantId)` is a pure, DB-free static method (throws `App\Identity\Exceptions\InvalidMembershipScopeException`, an `InvalidArgumentException` not implementing `HasErrorCode` since a violation is a programming bug, not user input, mirroring `App\Support\Tenancy\InvalidTenantIdException`), called from the model's `saving` event listener. `tests/Unit/Identity/MembershipScopeInvariantTest.php` exercises the static method directly, matching the plan's "Unit: ... the platform-scope invariant" line under Slice 3's own test list, landed here instead since the model exists now. Task-09's Actions inherit the guarantee automatically by going through `Membership::create()`/`save()`, without repeating the check.

**Deviation, investigated and resolved within this task, not deferred: `users` had no GRANT to `nodia_app`/`nodia_platform`.** Confirmed by direct psql probe against the running test database (`has_table_privilege('nodia_app', 'users', 'INSERT')` returned `false`) before writing any fixture code, per the CLAUDE.md verify-before-claiming rule. `memberships.user_id` is a real foreign key, and the isolation suite's connection is downgraded process-wide to the unprivileged `nodia_isolation` role (via `RlsHonestConnection`), so seeding a `User` row inside an isolation test's fixture requires `users` to be reachable under one of the two RLS group roles; without a grant, `nodia_isolation` has zero privilege on `users` under any role assumption, confirmed by a second probe (`probe_login`, a fresh unprivileged role granted membership in both group roles) against a throwaway RLS-protected table. `2026_07_09_000011_grant_users_table_to_rls_roles.php` adds `Rls::grantUnscoped('users')` (the same helper and justification already used for the Passport oauth tables: authentication infrastructure keyed to an identity, not tenant-scoped domain data, `users` carries no RLS at all per the plan). This is not purely a test-harness fix: task-09's `InviteUser` Action will need this same grant in production to create a new `users` row from inside a tenant-scoped `nodia_app` transaction, so landing it now, next to the migration that first requires it, avoids a retrofit later. Also empirically confirmed while investigating (not otherwise acted on, recorded for later stages' awareness): Postgres RLS `TO role` policies and plain table GRANTs are both satisfied by mere role *membership* with default `INHERIT`, with no `SET LOCAL ROLE` required; the codebase's explicit `SET LOCAL ROLE` pattern throughout Stage 1-3 does not add a privilege boundary beyond what persistent membership already grants, though it is unaffected here since `Rls::grantMembershipToCurrentUser()` only ever runs against the migration-time connection, not a persistent production runtime identity.

**Deviation: `Database\Factories\Identity\Models\{Role,Membership}Factory` cannot default `tenant_id` to `App\Tenancy\Models\Tenant::factory()`.** First attempt did exactly that (mirroring `TenantDomainFactory`'s own-context pattern) and failed `ContextBoundariesTest` (`Database\Factories\Identity` is not in that test's per-context factory exemption, only `Database\Factories\Tenancy` is exempt for `App\Tenancy\Models`). Both factories now omit a `tenant_id` default entirely, requiring every caller to pass a real tenant id explicitly; `App\Models\User` stays defaulted via `User::factory()` since it is not a bounded-context model (`App\Models`, not `App\{Context}\Models`) and so is unrestricted.
